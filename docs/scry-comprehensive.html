Scry

"See the future in your data." — A terminal SQL client built on LuaJIT, termbox2, and cooperative async.

01At a Glance

What it is

A fast, Vim-inspired TUI for querying relational databases — similar to Lazygit but for SQL. Single static binary. Phase 1: Postgres, MySQL, SQLite. Phase 2: MongoDB, Redis.

Why it exists

Most SQL clients block the event loop during queries — no keyboard input, no Ctrl+C, no UI updates. Scry's cooperative async model keeps the UI responsive even on 10-second queries.

03The Async Model

Why async is load-bearing, not a polish item

LuaJIT is single-threaded. A blocking execute() freezes the entire event loop — no repaint, no keyboard input, so Ctrl+C could never be received while a query runs at all.

04Driver Reality

The adapter contract promises async, but each driver delivers differently. The spec is honest about this asymmetry.

CapabilityPostgreSQLMySQL/MariaDBSQLite
query_async✓ PQsendQuery✓ mysql_real_query_start✗ prepare only
result_streaming✓ PQgetResult✗ store_result (all at once)✓ step per row
result_fetch_async✓ PQisBusy✗ blocks event loop✗ CPU-bound
early_close_drain✓ multi-result drain✗ free_result safe✗ finalize safe
Ctrl+C during query✓ next tick✓ next tick⚠ between steps
Ctrl+C during fetch✓ stop + drain✓ stop✓ stop per step
Postgres: full cooperative async

Libpq provides real socket-driven async. PQsendQuery dispatches without waiting. PQconsumeInput/PQisBusy checks readiness. PQgetResult retrieves when ready. Cancellation mid-query observable within one tick.

Cost: Early close requires draining multi-result sequences. close_result() enters DRAINING state progressing through poll().

MySQL: honest about the asymmetry

Query execution is async via MariaDB's mysql_real_query_start/_cont. But mysql_store_result() blocks during result transfer. Building against stock MySQL leaves MYSQL_OPT_NONBLOCK undefined — driver silently falls back to synchronous while exposing the async contract.

Phase 2 path: MariaDB's mysql_store_result_start/_cont for nonblocking result-fetch.

SQLite: local-file fast

poll() is a stub. No socket readiness. Ctrl+C observable between sqlite3_step calls, not inside. For recursive CTEs over large DBs, cancellation latency = remaining step time.

Phase 2 path: Direct FFI to sqlite3_interrupt(db).

05Key Tradeoffs

Every design decision trades one property for another.

1. Cancellation: close-and-reconnect vs native driver cancel
✓ Chosen: close connection, prompt reconnect
✗ Rejected: PQcancel / mysql_kill / sqlite3_interrupt via FFI
Why: Native cancel requires raw driver handles through LuaSQL — version-dependent userdata structs. Close-and-reconnect is uniform across all drivers, works through public API.
Cost: Slower than native cancel (full TCP handshake vs single packet).
Phase 2: adapter.cancel({ strategy = "native" }) per driver.
2. Multi-statement failure: halt-on-first vs run-all
✓ Chosen: stop at first failed Statement
✗ Rejected: run all, report per-statement
Why: Mid-buffer failure in BEGIN; ...; COMMIT; leaves ambiguous transaction state. Halting avoids committing on top of failure. Matches luasql's batch-abort behavior.
Cost: User must re-run remaining Statements manually.
Phase 2: --continue-on-error flag.
3. Row access: next_row() only vs materialize-everything
✓ Chosen: single row-pull primitive
✗ Rejected: get_result() returns all rows
Why: A materialize method defeats the memory guarantee. With next_row(), grid caps at max_result_rows while exports stream to file — same primitive, two consumers.
Cost: Each consumer implements own buffering. Two small implementations, one shared primitive.
4. Config: executable Lua vs YAML/TOML
✓ Chosen: Lua files returning tables
✗ Rejected: YAML, TOML, JSON
Why: Config needs os.getenv() for secrets, string concat for paths, functions for conditionals. Lua provides all natively with zero deps.
Cost: Project config is executable code. Untrusted repos could run arbitrary Lua.
Mitigation: Documented security implication in spec.
5. Parser: one shared module vs per-driver parsers
✓ Chosen: single streaming state machine
✗ Rejected: separate parsers per dialect
Why: Statement boundaries (semicolons outside strings/comments) are the same across dialects. One module ensures splitter, classifier, and highlighter agree — enforced by construction.
Cost: No dialect-specific parsing (PL/pgSQL blocks). Documented Phase 2 consideration.
Limitation: Nested block comments may mis-split.
6. Result paging: client-side vs server-side
✓ Chosen: client-side over capped result
✗ Rejected: rewrite SQL with LIMIT/OFFSET
Why: Rewriting user SQL breaks CTEs, subqueries, UNIONs, window functions. Client-side paging is predictable and doesn't touch user's SQL.
Cost: All paginated rows in memory. Cap is configurable (default 100k).
Phase 2: Server-side cursor for Postgres (DECLARE CURSOR / FETCH).
7. Dependency pinning: commit SHA vs tagged release
✓ Chosen: pin exact commit SHAs
✗ Rejected: use luasql 2.8.1 (latest release)
Why: Stock luasql 2.8.1 lacks async methods. PR #201 on master added them. No tagged release contains these.
Cost: Tracking master commit, not release. Requires build/SOURCES.txt for reproducibility.
8. Transactions: user-controlled vs auto-wrapped
✓ Chosen: BEGIN/COMMIT/ROLLBACK are ordinary Statements
✗ Rejected: adapter auto-wraps transactions
Why: Auto-wrapping creates hidden behavior. Explicit Statements give full control and simpler adapter contract.
Cost: Mid-failure may leave transaction open. UI shows rollback/reconnect/dismiss options.
9. Export: re-execute vs share grid cursor
✓ Chosen: re-execute single SELECT with fresh stream
✗ Rejected: export from grid's buffer
Why: Sharing cursor creates half-consumed state. Re-executing gives complete, correct export. Also prevents re-executing writes.
Cost: Export only for single read-only SELECT. Multi-statement and writes cannot export.
Benefit: Export streams to file, not bounded by max_result_rows.
10. CTE handling: scan-all vs blanket-block WITH
✓ Chosen: scan entire tokenized Statement for write keywords
✗ Rejected: block all WITH in read-only mode
Why: Blanket-blocking WITH loses legitimate read-only CTEs. Classifier already tokenizes the whole Statement — scanning for write keywords anywhere catches WITH x AS (DELETE ...) SELECT ... while allowing WITH x AS (SELECT ...) SELECT ....

07What's Missing

Critical path: Database adapters

Postgres (~400 lines) and MySQL (~400 lines). Every downstream feature depends on these. Postgres is higher priority — its full async model is what the event loop was designed around.

UI: grid, sidebar, status, modal

Grid is the largest new module (~500 lines): column sizing, pagination, sort, filter, null/binary rendering. Sidebar (~350) calls adapter catalog methods.

Utilities: read-only, export, history

Read-only (~100 lines) wraps existing parser classifier. Export (~280 lines) streams CSV/JSON. History (~150 lines) persists to JSONL.

Tests & fuzzing

Fuzz target (100k iterations, 2s timeout, 64KB max). Read-only, export, history unit tests. Postgres/MySQL integration tests. Driver capability verification.
